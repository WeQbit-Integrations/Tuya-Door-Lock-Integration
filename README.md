# Entrydesk

Visitor PIN management for the M-Link A6N using Tuya Smart Lock APIs, Firebase Authentication, Firestore and one Firebase callable Cloud Function. The app creates **online, multiple-use, seven-digit PINs** with a start and end time and offline one-time passwords. It does not create Tuya app accounts or recurring schedules.

## Before starting

- Rotate any Tuya client secret shared in chat or elsewhere. Never put it in browser configuration, source code, logs, or version control.
- Create a Firebase project with Authentication (email/password), Cloud Firestore, and a web app. Deploying 2nd-generation Firebase Functions requires the Blaze billing plan. Review Firebase and Tuya pricing, quotas, and subscriptions before deployment.
- In Tuya Cloud, link the Tuya Smart app account and lock to your cloud project, subscribe to the necessary Smart Lock APIs, and find the **device ID** and **data-center API endpoint**. API availability depends on your project and lock. See [Tuya Smart Lock Open APIs](https://developer.tuya.com/en/docs/cloud/smart-door-lock?id=K9jgsgd4cgysr).
- Install Node.js, the Firebase CLI, and Google Cloud CLI; authenticate them with accounts authorized to administer the Firebase project. Never share credentials in chat.

## Setup

1. Copy `.env.example` to `.env.local` and fill in the Firebase web app configuration from the Firebase console. These values identify your Firebase app; they are not the Tuya secret. Restart Vite after changing them.
2. Create an email/password user in Firebase Authentication. Public self-registration is not provided.
3. Configure the function's non-secret parameters in `functions/.env.<firebase-project-id>` (replace placeholders with your own values):

   ```dotenv
   TUYA_CLIENT_ID=your-tuya-client-id
   TUYA_DEVICE_ID=your-tuya-lock-device-id
   TUYA_ENDPOINT=https://openapi.tuyaus.com
   ```

   Select the endpoint for your Tuya project data center. Supported endpoints are listed in `functions/index.cjs`; use an exact URL without a trailing slash.
4. Set the rotated Tuya secret through the Firebase CLI. Enter it directly at the prompt, not in this chat:

   ```powershell
   firebase use YOUR_FIREBASE_PROJECT_ID
   firebase functions:secrets:set TUYA_CLIENT_SECRET
   ```

5. Grant the existing user an `admin` custom claim using Google Application Default Credentials. Replace the placeholders; never put a password or key in the command:

   ```powershell
   gcloud auth application-default login
   $env:GOOGLE_CLOUD_PROJECT = 'YOUR_FIREBASE_PROJECT_ID'
   node functions/grant-admin.cjs 'ADMIN_EMAIL'
   ```

6. Install dependencies and deploy rules, function, and hosting:

   ```powershell
   npm install
   npm install --prefix functions
   npm run build
   firebase deploy --only firestore:rules,functions,hosting
   npm run dev
   ```

   The function is in `us-central1`; keep the frontend's `VITE_FIREBASE_FUNCTIONS_REGION` aligned. A user whose admin claim was just granted must sign out and back in to refresh it.

## Using the app

Sign in as the authorized administrator, enter the visitor's name and time window, and generate the PIN. The PIN is saved with the visitor record and can be revealed in the register. All times are entered and displayed in the browser's local timezone and sent to Tuya as Unix timestamps.

Tuya accepting creation does not prove that the physical lock has received it. Use the row's **Check delivery** control, and test the PIN at the door with an alternative way inside before sharing it. Revocation is also asynchronous: confirm it at the lock. If a submission times out or is marked **Needs review**, check the Tuya app before retrying; the PIN may already exist.

The register loads current online temporary-password metadata from Tuya after administrator sign-in, and can be refreshed manually. Tuya does not return the existing PIN values. Passes created in the Tuya app appear read-only and must be managed there; website-created passes remain in Firestore. Offline passwords are not included. Tuya's list is cloud metadata and may not reflect the lock's current physical state. Expiry is enforced by the lock, not a scheduled Firebase function. Firestore reads the register directly; creation, refresh, explicit status checks, and revocation each invoke the single callable function once. There is no polling or scheduled function.

Select **One-time password** to generate an offline, single-use password. Tuya supplies its validity window, which is shown after generation. The separate register contains only one-time passwords generated by this website; it does not confirm whether a password has been used and does not provide revocation. Test compatibility with the actual lock before relying on a password. If Tuya generates a password but Firestore cannot save it, copy the displayed password immediately and check Tuya before retrying.

## Local Firebase emulators

Start the Firebase emulators and frontend in separate terminals:

```powershell
firebase emulators:start --project demo-entrydesk --only auth,firestore,functions
node functions/seed-local-admin.cjs
npm run dev:local -- --host 127.0.0.1
```

Open `http://127.0.0.1:5183/`. Emulator mode automatically signs in as the local administrator; run the seed command above after starting the emulators, then reload the page if needed. The local account is for the isolated emulator only and must never be used in a real project. Emulator data is temporary and the administrator needs to be seeded again after restarting without an emulator export. The Firebase Emulator UI is at `http://127.0.0.1:4000/`. Production mode still requires administrator sign-in.

This mode uses the demo Firebase project and does not connect to production Firebase. It does not simulate Tuya or the lock. If the ignored local configuration files are missing, create `functions/.env.demo-entrydesk` with `TUYA_CLIENT_ID=local-unconfigured`, `TUYA_DEVICE_ID=local-unconfigured`, and `TUYA_ENDPOINT=https://openapi.tuyaus.com` on separate lines, and create `functions/.secret.local` with `TUYA_CLIENT_SECRET=local-placeholder-not-a-real-secret` before starting the emulators. Replace these placeholders only with your own correct Tuya project values and rotated secret to enable real lock requests. These files are local and must not be committed. PIN creation will contact the real Tuya service if valid credentials are configured. Do not rely on an unconfirmed PIN.

## Security and verification

Only users with the Firebase `admin` custom claim can read the register or call the function. Visitor PINs are stored as plaintext fields in Firestore and are accessible to administrators and privileged Firebase project personnel; Firestore provides encryption at rest. Client writes are blocked by Firestore rules. The Tuya client secret is available only to the server function via Secret Manager. Treat Firebase admins as trusted lock administrators, use strong authentication and restrict who can grant claims. Emulator mode automatically signs in to the local emulator and must not be exposed on an untrusted network. Enable App Check and additional monitoring before public deployment.

Run `npm run lint`, `npm run build`, and `npm test --prefix functions` for local checks. To include the PIN storage and security-rules test, start the Firestore and Auth emulators first, then run `$env:RUN_FIREBASE_EMULATOR_TESTS='1'; npm test --prefix functions; Remove-Item Env:RUN_FIREBASE_EMULATOR_TESTS`. The tests do not contact Tuya or the lock. Live operation requires a configured Firebase project, Tuya project/API permissions, device ID, and a physical lock test.
